IT Help Desk Management System

Technical Documentation, Architecture & Drawbacks Analysis

How The System Works

This system operates on a 3-tier architecture to track IT incidents and enforce SLA deadlines automatically.

1. The Frontend (User Interface)

A Single Page Application (SPA) built purely with HTML, CSS, and Vanilla JavaScript. It displays real-time statistics, dynamically highlights SLA-breached tickets in red, and provides interactive Modals to create or update tickets without reloading the browser.

2. The Backend (Node.js API)

The middle layer powered by Node.js and Express. It receives HTTP requests, executes business logic, and communicates with the database via a connection pool. It also runs a silent Cron Job every 5 minutes to trigger the SLA Escalation procedure.

3. The Database (MySQL)

The permanent storage layer containing Tables and Stored Procedures. It manages relations between Users, Tickets, and the chronological Activity Logs.

The Incident Lifecycle

  • Creation: A ticket is submitted. The Database runs set_sla_deadline to calculate exact resolution deadlines (1, 4, 8, or 24 hours).
  • Tracking: Any status or assignment change automatically inserts an audit trail into the Activity Log.
  • Escalation: If a ticket is unresolved past its deadline, the background worker invokes escalate_breached_tickets to automatically bump the support tier (L1 → L2 → L3) and flag it.

System Drawbacks & Limitations

While this prototype demonstrates deep full-stack proficiency, it has intentional limitations regarding enterprise readiness:

1. Lack of Authentication

The system blindly trusts the frontend. User IDs (like the Requester ID or Agent ID) are currently hardcoded. In a production environment, an Authentication flow (like JWTs or Sessions) must be implemented.

2. No Database Pagination

The "All Tickets" view currently queries and returns every single ticket in the database. For tens of thousands of tickets, this will crash the browser. We would need to implement SQL `LIMIT` and `OFFSET` pagination.

3. Vanilla JS Maintenance Overhead

Using pure JavaScript proves a strong grasp of the DOM, but managing state across a large app without a framework like React or Vue.js eventually leads to unmanageable code complexity.

4. Cron Job Scalability

The 5-minute `setInterval` works on a single server instance. If the backend is horizontally scaled across 5 servers, all 5 would attempt to escalate tickets simultaneously, causing race conditions. A dedicated message queue (like Redis) is required.

Implementation Walkthrough

Database Schema Built

  • Created 3 relational tables: users, tickets, ticket_logs.
  • Implemented ON DELETE CASCADE so removing a ticket automatically cleans its logs.
  • Created 2 Stored Procedures to offload complex SLA math to the MySQL layer.

Backend API Routes

Developed exactly 7 RESTful endpoints:

  • GET /api/tickets - Fetches tickets with SQL JOINs to populate user names dynamically.
  • GET /api/tickets/stats - Runs aggregate counts (Total, Open, Escalated) for the dashboard.
  • POST /api/tickets - Validates descriptions and handles the ticket creation flow.
  • PATCH /api/tickets/:id - Modifies status, assigns users, and auto-generates activity logs.
  • POST /api/tickets/sla/run-escalation - Manual override to trigger the breach logic.

Frontend Engineering

  • Enforced strict CSS rules using Custom Properties (Variables) for theme colors without external libraries.
  • Engineered custom CSS Modals and a Toast Notification system for user feedback.
  • Handled complex DOM string interpolation to render dynamic tables.

Setup & Execution

  1. mysql -u root -p < schema.sql (Creates DB)
  2. Update the .env file with MySQL credentials.
  3. npm install (Installs Express & MySQL2)
  4. npm start (Boots the server)
  5. Open index.html in a browser!
